Пользователь: death@predatorg3571, Ubuntu 24.04. Рабочее дерево теперь

команды блоками для копирования. Пользователь делает все прогоны на
железе и присылает результаты (файлы png/tiff/dat, вывод скриптов); решения
принимает он. Правки в код только по явной команде «давай/сделай». Перед
серией сканов сканер иногда выключить-включить. Не хардкодить константами
то, что можно посчитать из данных сессии, — это требование пользователя.

**ЖЁСТКОЕ ПРАВИЛО НАВСЕГДА.** Каретка ездит только вперёд. Никогда не
предлагать команды и правки, при которых калибровочный проход заканчивается
дальше начала скана (y_offset 34 мм + tl_y), и никогда не ставить
model.y_offset в 0 или меньше конца калибровки. Оба раза, когда это было
нарушено (y_offset=0; OB4800_CALIB_Y_MM=40 при -t 0), каретку загнало в
упор с хрустом. При съёмке эталона с OB4800_CALIB_Y_MM=40 скан обязательно
с `-t 20` (с 60 — `-t 40`). Перед каждой командой с движением проверять
условие явно и писать это первой строкой ответа. В коде есть защита
(patch_guard.py), но правило остаётся. Тёмный проход с выключенной лампой
каретку не двигает (мотор не стартует).

Сканер: Plustek OpticBook 4800, USB 07b3:1301, чип GL845, CCD, LED-лампа.
Чип GL845 обслуживается **gl846.cpp** (не gl843 — один патч по ошибке лёг
туда и был откачен). Поддержка сделана в backend `genesys` как отдельная
модель `PLUSTEK_OPTICBOOK_4800` (3800 не тронут).

## Что сделано после v4 (главная находка этапа)

**Калибровку затенения надо снимать в том же окне по x и том же режиме
считывания CCD, что и скан.** genesys калибрует всегда трёхканально с
нулевого пикселя; на полном такте (1200) такой проход не видит узких
дефектов отклика линейки (пыль в тракте, ~30 px, −5…−7 %) — эталон их не
содержал, и они оставались вертикальными полосами. Теперь на 1200 окно
калибровки = окно скана (startx 183, 9920 px, считается из сессии скана),
серый калибруется в один канал, цвет в три, тёмное меряется проходом с
выключенной лампой. Результат: 1501 −6.5 % → −0.9 %, 6910 −5.6 % → −1.0 %
(серый), −0.3…−1.3 % по каналам (цвет). Подробности и все ловушки — в
НАХОДКИ-GL845 пп. 17–26 и в README.

Ключевые факты для того, кто продолжит:
- одноканальный проход с нулевого пикселя чип на полном такте не
  выполняет (bulk_read timeout, USB требует выключить-включить); со 183-го
  выполняет; трёхканальный — с любого;
- в одноканальной сессии чип отдаёт ровно `lines` строк, generic-код ждёт
  `lines+1` — читать `min(size, total_bytes_to_read)`;
- фазы CCD 0x52–0x57 между калибровкой и сканом различаются, но на
  результат не влияют — не тратить на них время;
- на 300/600 одноканальная калибровка даёт клин −60 % на нуле, там она не
  нужна (полос нет) — правило включается по `shading_resolution ==
  full_resolution`;
- `white_average_data` и файл эталона — от нулевого пикселя сенсора с
  нулями до старта окна, `pixels_per_line` включает старт; резать со
  смещением нельзя;
- `calib_session` заполняется внутри `genesys_shading_calibration_impl`;
  условия в `genesys_flatbed_calibration` брать по `settings` и `sensor`;
- пьедестал АЦП (лампа выкл) 3.0/255; тёмное по холостым столбцам на полосе
  (20.3/255) завышено засветкой — на 300 чёрное срезается в 0, на 1200
  чёрный тонер честно даёт 36/255. Это чёрная точка, не калибровка.

## Скрипты этого этапа (все с --revert), в порядке применения

В `~/` и в `patches-history/` пакета:
1. `patch_whiteref2.py` — перебазирование эталона на живое тёмное (закрыло
   светлую зону 8–25 мм слева, пункт 1a из v4).

   окно скана; заголовок эталона `OB4800WREF2 <px> 3 <startx>`; загрузчик
   берёт первые pixels_per_line записей при fs ≤ startx и fp ≥ px.
5. (`patch_calib_offset.py` — применён и **откачен**, мёртвый код.)
6. `patch_calib_1ch_1200.py` — одноканальная калибровка только на полном
   такте.
7. `patch_dark_pass.py` + `patch_dark_pass2.py` — тёмный проход с
   выключенной лампой на полном такте, условие по settings/sensor.
8. `patch_color_1200.py` — окно скана, тёмный проход и точный размер чтения
   на полном такте независимо от каналов (цвет 1200).
9. `patch_target_single.py` — одна цель 0xa400 вместо трёх констант.
10. `patch_log_text.py`, `patch_comment_dark.py` — текст лога и комментарий.
11. `patch_xsize.py` — x_size 215.9 → 212.7 (конец сенсора, без нулевых

A/B-переключатели: `OB4800_CALIB_3CH`, `OB4800_NO_DARK_PASS`,

`OB4800_SHADING_TEST`, `OB4800_SHADING_SHIFT`, `OB4800_AFE_GAIN_DELTA`

перепутаны, описано в инструкции). `SANE_DEBUG_GENESYS_IMAGE=1` пишет дампы
(`gl_white_*`, `gl_black_*`) в **текущий каталог**.

## Закрытые вопросы по краям (08.09, не переоткрывать)

- Зазор ~9 мм между листом у левого упора и правым пластиком: 3.2 мм видит
  сенсор (в кадре), ~6 мм — стекло без линейки, не сканирует никто.
- Нули справа на 300 dpi при скане документа — темнота за краем документа
  (крышка), не конвейер: с альбомным листом нулей нет ни на одной группе.
- Чёрная полоса 0.6 мм при запросе A4 — подложка за краем листа, потому
  что кадр начинается на 0.5 мм внутри листа. Сдвиг кадра на край листа
  перенёс бы полоску на левый упор — не делать. Позиция Almsit: это
  реальность стекла, её нужно видеть; драйвер ничего не режет и не
  дорисовывает. В simple-scan своего размера страницы НЕТ (только список
  форматов) — совет «задать 208.6» был ошибочным, не повторять; ширину
  числом дают scanimage -x, xsane, gscan2pdf.

## Команды

Сборка после правок:
```
cd ~/sane-upstream && make -j$(nproc) 2>&1 | grep -E " error"; sudo make install >/dev/null && sudo ldconfig
sudo cp /usr/local/lib/sane/libsane-genesys.so.1.4.0 /usr/lib/x86_64-linux-gnu/sane/
sudo ln -sf libsane-genesys.so.1.4.0 /usr/lib/x86_64-linux-gnu/sane/libsane-genesys.so.1
sudo ldconfig
rm -f ~/.sane/plustek-opticbook-4800.cal
```
В `/usr/local/lib/sane/` лежат обе версии (1.2.1 от старого дерева и 1.4.0
от нового), симлинк `libsane-genesys.so.1` указывает на последнюю
установленную — при путанице проверять `ls -la`.
Скан через нашу сборку:
```
SANE_CONFIG_DIR=/usr/local/etc/sane.d LD_LIBRARY_PATH=/usr/local/lib \
  /usr/local/bin/scanimage -d genesys --mode Gray --format=png --resolution 300 -l 0 -t 0 -x 210 -y 297 > ~/out.png
```
Профиль по белому листу: `python3 ~/prof.py файл.png dpi` (полосы по y,
шаг 2 мм, линейные проценты с учётом гаммы 1.7). Провалы по колонкам:
`ripple.py`, `oddeven.py`, `dipcmp.py` в `~/`. Лог регистров:
`SANE_DEBUG_GENESYS=255`, разбор по `address: 0x...., value: 0x..`, фазы
`init_regs_for_shading` против `init_regs_for_scan` (см. НАХОДКИ).
